An AI assistant that lives on your machine.

Yggdrasil is a personal, self-hosted assistant: local models of your choosing, neural search over one SQLite file, and a background service that survives reboots. Your chats, embeddings, and secrets stay in a single directory behind your own login. Nothing is sent anywhere unless you point it somewhere.

curl -fsSL https://raw.githubusercontent.com/anjasta-tarigan/yggdrasil/main/install.sh | bash

The script verifies itself against its published SHA-256 before it runs, then builds, registers a background service, and waits for the health check to answer.

What grows out of it

Everything below ships in the default build. Each piece can talk to the outside world or refuse to, depending on what you configure.

Models, your pick

Run Ollama on the same box, connect any OpenAI-compatible endpoint such as vLLM, LM Studio, or LocalAI, or point at an NVIDIA NIM enterprise endpoint. Inference happens where you decide inference happens.

An experimental DeepSeek web adapter is also available, opt-in through a configuration flag, with credentials encrypted at rest.

Memory that is one file

Embeddings live in SQLite with the sqlite-vec extension alongside FTS5 full-text search; optional cross-encoder reranking runs on-device via an ONNX build of bge-reranker-v2-m3 and evicts its memory when the machine idles. No database server, no managed vector cloud. One file holds the whole memory.

Workspaces and agents

Chat lives in project workspaces with their own directories, instructions, and trust levels. A collapsible file explorer inspects what the assistant touched, reasoning traces stream in as they happen, and background subagents can run tools inside a sandbox you delegate explicitly.

Tools that check twice

Web search and page fetching, multi-backend image search, and sandboxed file and shell tools. The shell and file tools stay off until you switch them on in Settings, and every outbound fetcher rejects private addresses and cloud metadata endpoints.

A real service, not a terminal tab

The installer registers a proper background service under systemd on Linux, launchd on macOS, or Task Scheduler on Windows, then keeps it running across reboots. Updates stop the service, back up the database, rebuild, and roll the whole thing back to the previous commit if any step fails.

Where it lives

The installer puts everything under one home directory. The checkout can be deleted and re-cloned at will; the data next to it is the part that must survive. 

~/.yggdrasil/
├── app/                       # Git checkout; the build runs here
│   ├── .env -> ../.env
│   └── data -> ../data
├── data/                      # Canonical state; survives updates
│   ├── yggdrasil.db           # sessions, messages, embeddings
│   ├── providers.json         # provider configuration
│   ├── providers.secrets.env  # API keys, mode 0600
│   ├── models/                # ONNX embeddings and reranker
│   ├── backups/               # database snapshots before updates
│   └── logs/                  # service stdout and stderr
└── .env                       # APP_SECRET, mode 0600
yggdrasil.db
The whole mind of the system: sessions, messages, and vector embeddings in one SQLite file.
providers.secrets.env
API keys with owner-only file permissions. Session tokens are encrypted in the database with keys derived from APP_SECRET.
models/
ONNX models for on-device embeddings and reranking, downloaded once and reused forever.
backups/
Timestamped database snapshots taken before every update, so a failed build rolls back to a working copy of itself.
.env
Contains the 32-byte APP_SECRET generated at install time, written with mode 0600 and linked into the app directory.

Install

One command. The script has to prove it is the one the release was signed with before any of your disk is touched.

  1. Linux and macOS
    curl -fsSL https://raw.githubusercontent.com/anjasta-tarigan/yggdrasil/main/install.sh | bash
  2. Windows (PowerShell)
    irm https://raw.githubusercontent.com/anjasta-tarigan/yggdrasil/main/install.ps1 | iex

What happens next, in order: prerequisites are checked, the release tag is checked out, dependencies install under Node 24, the production build compiles, a background service registers, and the page opens at http://127.0.0.1:2302. Re-running the script updates an existing install in place.

Pins and knobs, set as environment variables before the command.
VariableWhat it does
YGGDRASIL_VERSION=v0.6.0 Install a specific release instead of the latest one.
YGGDRASIL_CHANNEL=main Skip the release gate and track the main branch, for development installs.
GITHUB_TOKEN Optional. Raises the GitHub API rate limit while resolving the latest release.

Once it is running

The installer links a single command into your path. It talks to the service, not to screenfuls of process output.

CommandWhat it does
yggdrasil statusService status and the active HTTP port.
yggdrasil startStart the background service.
yggdrasil stopStop the running service.
yggdrasil logsTail the service stdout and stderr.
yggdrasil updatePull latest, back up the database, rebuild, roll back on failure.
yggdrasil check-updateCheck for a newer release without downloading it.
yggdrasil uninstallRemove the service and app files. Add --purge to delete the data too.

On Windows an icon also sits in the notification area: open Yggdrasil from it, or right-click for start, restart, and update actions.

What it protects

These are design invariants, not slogans. Each one is enforced in code and covered by the installer and CI.

  • Verified distribution

    The bootstrap script re-downloads the installer from the pinned release, checks it against the published SHA-256, and refuses plain HTTP or downgraded redirects. The checksums are regenerated in CI, so they always match the published files.

  • Encrypted credentials

    Session tokens and provider secrets are encrypted with AES-256-GCM using keys derived from APP_SECRET, which is generated at install time and never leaves the machine.

  • Network defenses

    Outbound fetches validate protocols and reject loopback, RFC 1918 private subnets, and cloud metadata addresses, so a malicious page cannot use the assistant as a proxy into your network.

  • Mutation route gates

    Every mutating route enforces strict Origin and Referer checks plus sliding-window rate limits.

  • Sandbox by default

    Shell and file tools start disabled and run only with explicit user permissions. Subagents get tool access only through explicit sandboxed delegation.

Found something? Please report it privately through GitHub's security advisory flow rather than a public issue. The process is described in SECURITY.md, and reports with real impact receive credit in the release notes.
